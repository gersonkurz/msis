# T1 — `preserve="yes"` runtime probe

Closes the runtime half of [#5](https://github.com/gersonkurz/msis/issues/5), recorded as
**T1** in `todo-testme.md`. Issue #5 proved the XML msis emits and that WiX compiles it at
1500 values. It never proved what Windows Installer *does* with it. This does.

## What it checks

Six values, one per unknown, seeded to look like a machine that has been running the
product, then compared against what the change predicts:

| Value | Seeded before install | Expected after | Type | Why it is here |
|---|---|---|---|---|
| `Absent` | *(not present)* | `default-absent` | `REG_SZ` | the `.reg` default must win |
| `AbsentDword` | *(not present)* | `42` | `REG_DWORD` | landing as `REG_SZ "42"` is a real defect |
| `Existing` | `live-existing` | `live-existing` | `REG_SZ` | the point of `preserve=`, and the elevated handoff |
| `ExistingDword` | `99` | `99` | `REG_DWORD` | same, where the `#` prefix has to round-trip |
| `EmptyExisting` | `""` | the default — **not** `""` | `REG_SZ` | issue #26: empty live values are NOT preserved |
| *(unnamed)* | *(not present)* | `default-unnamed` | `REG_SZ` | RegLocator documents this case differently |

Then: the key must be **gone** after uninstall.

`EmptyExisting` is the row that surprised. It was expected to keep the empty value; it does
not. The search runs and reads the empty value, but AppSearch makes no assignment from an empty
result — no `PROPERTY CHANGE` line appears for it — so the property keeps the `.reg` default
it was initialised with, and that default is written. A user who deliberately blanked a setting
gets it back. msis-2.x behaves the same way, so this is long-standing rather than a regression.
Tracked as **#26**.

The table above therefore records what the code **does**, so re-running this detects a change
in any of the six rows. If #26 is fixed, flip that expectation back to `""` in the same change.

## Running it

```powershell
uv run t1_preserve_probe.py --build-only   # no elevation: writes fixtures, builds the MSI
```

then, from an **elevated** shell:

```powershell
uv run t1_preserve_probe.py                # silent (/qn)
uv run t1_preserve_probe.py --ui           # full UI - click through the wizard
```

Both passes are required. Windows Installer skips AppSearch in the execute sequence when
the UI sequence already ran it, so the two paths can disagree — and if they do, that is
itself the finding.

## What it touches

- `HKLM\SOFTWARE\MsisPreserveProbe` — deleted and recreated each run. Nothing else in the
  registry is read or written.
- Installs and then uninstalls a per-machine MSI called **Msis Preserve Probe**. The
  uninstall also runs if the install fails or you cancel the wizard, so nothing is left
  behind.
- Builds `msis.exe` from this working tree, and passes `/TEMPLATEFOLDER` pointing at the
  repo's `templates/`. Both deliberate: the probe must test the code in this repo, not the
  installed copy, which has silently invalidated probes before.

## Output

Everything goes to the console and to `t1-probe.log`. The MSI's own verbose log lands in
`install-qn.log` / `install-ui.log`, and the script pulls the
`PROPERTY CHANGE ... PS_RV_` lines out of it — those lines are the mechanism visibly
working or not working.

Exit code is 0 when every row matches, 1 when any row does not.

## If a row does not match

Do **not** reinstate the per-value `SetProperty` — that is the #5 bug, and it is what made
a few hundred preserved values unbuildable. Open a new issue with this output and link it
from #5.

## Files

`pyproject.toml`, `README.md` and `t1_preserve_probe.py` are the project. Everything else
here — `rtprobe.reg`, `rtprobe.msis`, `readme.txt`, `rtprobe.wxs`, `rtprobe.msi`,
`msis.exe`, the logs — is generated by the script and safe to delete.
